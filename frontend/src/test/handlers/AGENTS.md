# frontend/src/test/handlers/

**Função**: handlers MSW que simulam a API nos testes, um arquivo por recurso, tipados pelo `schema.gen.ts`.

**Entra aqui**:

- `index.ts`: reexporta tudo e define `handlers`, os padrões do servidor (caminho feliz: instância configurada, usuário logado, API pronta).
- `errors.ts`: `apiErrorResponse(status, code, details?)`, resposta no formato de erro padrão.
- `health.ts`: `healthReadyOk` (padrão), `healthReadyUnavailable`, `healthReadyNetworkError`, `healthReadyPending`.
- `setup.ts`: `setupStatusDone` e `setupOk` (padrão), `setupStatusNeeded`, `setupStatusServerError`, `setupAlreadyCompleted`.
- `auth.ts`: `meOk`, `updateProfileOk` (`PATCH /v1/me`, aplica o corpo ao usuário padrão), `loginOk`, `logoutOk`, `logoutAllOk`, `csrfOk` (padrão), `logoutAllFails(status, code)`, `meAs(me)`, `meUnauthenticated`, `meServerError`, `updateProfileCsrfFailed`, `loginInvalidCredentials`, `logoutUnauthenticated`, `logoutCsrfFailed`.

- `recovery.ts`: `forgotPasswordOk`, `resetPasswordOk` e `verifyEmailOk` (padrão, 204), `forgotPasswordServerError`, `resetPasswordInvalidToken`, `resetPasswordWeak`, `verifyEmailInvalidToken`, `verifyEmailServerError`.
- `invites.ts`: `invitationPreviewOk` e `acceptInvitationOk` (padrão: convite de editor para `bruno@example.test`, sem conta; o aceite devolve o `me` do convidado já membro), `invitationPreviewAs(preview)`, `invitationPreviewInvalidToken`, `acceptInvitationLoginRequired`, `acceptInvitationEmailMismatch`, `acceptInvitationInvalidToken`, `acceptInvitationAlreadyMember`.
- `account.ts`: `sessionsOk` (lista padrão: esta sessão e um celular, paginada por `limit`/`offset`), `revokeSessionOk`, `changePasswordOk` e `resendVerificationOk` (padrão), `sessionsAs(sessions)`, `sessionStore(initial)` (GET + DELETE com estado: a sessão revogada some da próxima listagem; `revoked` guarda os ids), `sessionsServerError`, `revokeSessionCsrfFailed`, `changePasswordInvalidCurrent`, `changePasswordWeak`, `resendVerificationAlreadyVerified`, `resendVerificationTooMany(seconds)`.
- `members.ts`: membros, convites e nome do workspace (`/v1/workspaces/{id}`, `/members`, `/invites`). Padrões sem estado: `membersOk`, `changeMemberRoleOk`, `removeMemberOk`, `invitesOk`, `createInviteOk`, `revokeInviteOk`, `resendInviteOk`, `renameWorkspaceOk`. Com estado, criados por teste: `memberStore(initial)` (PATCH/DELETE mudam o próximo GET; `changes`, `removed`) e `inviteStore(initial)` (POST/DELETE/resend; `created`, `revoked`, `resent`). Variações: `membersAs`, `invitesAs`, `membersServerError`, `invitesServerError` e `<ação>Fails(status, code)` para cada mutação.
- `audit.ts`: auditoria do workspace (`"workspace"`) e da instância (`"instance"`). Padrões `workspaceAuditOk` e `instanceAuditOk` (lista de `makeAuditEvents`, paginada, filtros ignorados); `auditAs(scope, events)`, `auditRecorder(scope, events)` (guarda a query string de cada requisição em `queries`), `auditServerError(scope)`.
- `admin.ts`: `/v1/admin/workspaces` e `/v1/admin/users`. Padrões em `adminHandlers` (listas com busca por `q`, mutações respondendo com a linha alterada). Com estado: `adminWorkspaceStore(initial)` (POST com 409 `slug_taken` para identificador em uso, PATCH; `created`, `changes`, `queries`) e `adminUserStore(initial)` (PATCH; `changes`, `queries`). Variações: `adminWorkspacesAs`, `adminUsersAs`, `adminWorkspacesServerError`, `adminUsersServerError`, `createWorkspaceFails`, `updateWorkspaceFails`, `updateUserFails`.
- `providers.ts`: `/v1/workspaces/{id}/providers` e `/test`. Padrões sem estado: `providersOk`, `createProviderOk`, `updateProviderOk`, `deleteProviderOk`, `testProviderOk`. Com estado: `providerStore(initial, { inUse, testResults })` (POST com 409 `provider_name_taken`, PATCH, DELETE com 409 `provider_in_use` para os ids em `inUse`, teste com o resultado de `testResults` ou sucesso; chaves só mascaradas; `created`, `changes`, `deleted`, `tested`). Variações: `providersAs`, `providersServerError`, `failedTest(code, status)` (resultado `ok: false`) e `<ação>Fails(status, code)`.
- `products.ts`: `/v1/workspaces/{id}/products` (produtos, plano 0009). Padrões sem estado: `productsOk`, `createProductOk`, `updateProductOk`, `deleteProductOk`. Com estado: `productStore(initial, { webhookTest })` (POST com 409 `product_name_taken`, PATCH (`ticket_webhook_url: null` desliga), DELETE; mensagem de "sem fonte" vazia vira `DEFAULT_NO_SOURCE_MESSAGE`; `collection_ids` e `min_similarity` omitidos no POST viram `[]` e `DEFAULT_MIN_SIMILARITY`, como no backend; `.../ticket-webhook/secret` devolve `WEBHOOK_SECRET` com `WEBHOOK_SECRET_CREATED_AT` e `ticket_webhook_configured` segue URL e segredo; `.../ticket-webhook/test` responde `webhookTest` (padrão `makeWebhookTest()`, aceito com 204, ou um `Response` de erro); `created`, `changes`, `deleted`, `secretRotations`, `webhookTests`). Variações: `productsAs`, `productsServerError`, `<ação>Fails(status, code)` (`updateProductFails` aceita `details`) e `rotateWebhookSecretFails`. Duplicar: `duplicateProductRecorder(copy)` (padrão: "Suporte ERP (cópia)" com `DUPLICATED_PRODUCT_ID`; `requests` com o id do original e o corpo) e `duplicateProductFails`.
- `levels.ts`: `/v1/workspaces/{id}/levels` e `/levels/{level}` (níveis de resposta do workspace). Padrão `workspaceLevelsAs()` (com `makeWorkspaceLevels()`); com estado, `levelStore(initial)` (o PATCH aplica os campos como o backend: `instructions: null` volta ao padrão e marca `instructions_is_default`, `provider_id`/`model` nulos desligam o nível, nome e tipo da credencial vêm de `makeProviders()`; `changes`). Variações: `workspaceLevelsServerError`, `updateLevelFails(status, code)`.
- `collections.ts`: `/v1/workspaces/{id}/collections`, o detalhe e `/search`. Padrões em `collectionsHandlers` (`collectionsAs()` com Código ERP e Manuais, lista e detalhe (404 para outro id); `createCollectionOk`, `updateCollectionOk`, `deleteCollectionOk`; busca com os dois resultados padrão). Com estado: `collectionStore(initial)` (POST com 409 `collection_name_taken`, PATCH com 409 `collection_embedding_locked` ao mudar credencial ou modelo de coleção com documentos, DELETE com 409 `collection_in_use` quando há fontes; `created`, `changes`, `deleted`). `searchRecorder(results)` guarda os corpos em `bodies`. Variações: `collectionsServerError`, `collectionServerError`, `searchFails` e `<ação>Fails(status, code)`. "Sincronizar todas": `collectionSyncAs(result)` (202, padrão nada iniciado nem pulado; `synced` com os ids) e `collectionSyncFails(status, code)`.
- `sources.ts`: `/v1/workspaces/{id}/sources` (lista filtrada por `collection_id` como a API, detalhe, CRUD, `/test`, `/sync`, `/cancel`, `/runs`, `/documents`) e `/v1/workspaces/{id}/runs/{run_id}`. Padrões sem estado em `sourcesHandlers` (erp-core, suas execuções sem erros, seus documentos filtrados por `path` e `kind`, mutações que funcionam). Com estado: `sourceStore(initial, { runs, errors, documents, testResults, levelForbidden })` (POST com 409 `source_name_taken` e `min_level` omitido como o padrão do tipo, PATCH (`schedule_cron: null` limpa; `min_level` recalcula `min_level_is_default`, ou 403 `forbidden` com `levelForbidden`), DELETE, teste com o resultado de `testResults` ou sucesso, sync que cria a execução `queued` com 409 `source_inactive` e `sync_already_running`, cancel com 409 `sync_not_running`, reindex como o sync e com 409 `source_reindex_unsupported` para chamados e cards (`reindexed`), erros da execução paginados por `errors_limit`/`errors_offset`; `finishRun(sourceId, status)` simula o worker; `created`, `changes`, `deleted`, `tested`, `synced`, `cancelled`, `documentQueries`, `reads`). Variações: `sourcesAs(sources)`, `sourcesServerError`, `sourceServerError`, `sourceRunsServerError`, `runServerError`, `sourceDocumentsServerError`, `sourceActionFails(action, status, code)`.
- `tickets.ts`: fontes por push, chamados e cards: `/v1/workspaces/{id}/sources/{source_id}/ingest-token` e, para cada tipo, `/<tickets|cards>/summary`, `/upload` e `/preview`. Padrões em `ticketsHandlers` (resumo, token, relatório e prévias de `../ticketFactories.ts`). `ticketStore({ token, report, preview, cardPreview, summary })` (o resumo passa a ter o prefixo e a data de cada token gerado; `summaryReads()` conta as leituras) guarda `rotations`, `uploads` (ids das fontes de cada upload `multipart/form-data` com a parte `file`; sob jsdom o `fetch` do Node envia o `File` do jsdom vazio, então o teste confere o arquivo espiando `FormData.prototype.append`), `uploadKinds` (o tipo da rota de cada upload) e `previews` (`{sourceId, kind, body}`). Variações, listas de handlers (use com `...`): `ticketActionFails(action, status, code, details)` (`token`, `upload`, `preview`, nos dois tipos) e `ticketsSummaryServerError`.
- `memberLevels.ts`: `/v1/workspaces/{id}/member-levels` e `/members/{user_id}/product-levels`. Padrões em `memberLevelsHandlers` (`memberLevelsAs()` com `makeMemberLevels()` e `makeProductRefs()`, filtrado por `query` e `role` como a API; `PUT` que responde a linha padrão alterada). Com estado: `memberLevelStore({ products, members })` (`PUT` com `null` de volta ao padrão do papel, 404 `not_found`, 422 `member_level_product_invalid`; `changes`, `queries`). Variações: `memberLevelsServerError`, `setMemberLevelFails(status, code)`.
- `runners.ts`: `/v1/workspaces/{id}/runners` e `/{runner_id}`. Padrões sem estado em `runnersHandlers` (`runnersOk` com `makeRunners()`, criação que devolve `RUNNER_TOKEN`, revogação e exclusão que funcionam). Com estado: `runnerStore(initial, { inUse })` (POST com 409 `runner_name_taken` e o token, PATCH que renomeia e revoga (`revoked: false` em revogado → 422 `runner_revoked`), DELETE com 409 `runner_in_use` para os ids em `inUse`; `created`, `changes`, `deleted`). - `apiKeys.ts`: `/v1/workspaces/{id}/api-keys`, `/{api_key_id}` e `/revoke`. Padrões sem estado em `apiKeysHandlers` (`apiKeysAs()` com `makeApiKeys()`, criação que devolve `API_KEY_SECRET`, edição e revogação que respondem). Com estado: `apiKeyStore(initial, productIds)` (POST com 409 `api_key_name_taken` e 422 `api_key_product_invalid` para id fora de `productIds` (padrão: os de `makeProducts()`), PATCH de nome, escopo e `max_level` (corpo vazio 422, revogada 409 `api_key_revoked`), revogação idempotente; `created`, `changes`, `revoked`). - `harness.ts`: `/v1/workspaces/{id}/sources/{source_id}/modules`, `/harness-jobs` e `/v1/workspaces/{id}/harness-jobs/{job_id}` (e `/cancel`). Padrões sem estado em `harnessHandlers` (módulos de erp-local, uma tarefa rodando e uma concluída, detalhe sem rejeições, mutações que respondem). Com estado: `harnessStore(modules, { jobs, rejections, forceSkip })` (POST de módulo com 409 `module_key_taken` e chave derivada do título, PATCH que torna manual ao mudar título ou padrões, lote com 404 `module_not_found` e pulos `module_disabled`/`already_queued` (ou o motivo forçado em `forceSkip`), detalhe com rejeições paginadas, cancel com 409 `job_finished`; `finishJob(jobId, status)` simula o runner; `created`, `changes`, `enqueued`, `cancelled`, `moduleReads`, `jobReads`, `rejectionQueries`). - `knowledge.ts`: `/v1/workspaces/{id}/sources/{source_id}/knowledge`, `/{item_id}` e `/export`. - `dashboard.ts`: painel do workspace, painel e saúde da instância e acesso de superadmin. Padrões em `dashboardHandlers` (`makeWorkspaceDashboard`, `makeInstanceDashboard`, `makeInstanceHealth`; `enter` e `workspace-access` respondendo um `me`). Com estado: `workspaceAccessStore(base, names, startIn?)` (`GET /v1/me` começa em `base` ou já com acesso a `startIn`; `enter` dá o acesso ao workspace do caminho e o `DELETE` volta a `base`; `entered`, `left`); `meWithAccess(id, name, base)` monta o `me` com o acesso (item `access: superadmin`, papel admin). Variações: `workspaceDashboardAs`, `workspaceDashboardPending`, `workspaceDashboardServerError`, `instanceDashboardAs`, `instanceDashboardServerError`, `instanceHealthAs`, `instanceHealthServerError`, `enterWorkspaceFails`, `leaveWorkspaceAccessFails`.
- `usage.ts`: `/v1/workspaces/{id}/usage` e `/usage.csv`. Padrão em `usageHandlers` (relatório de `makeUsageReport` para o `group_by` pedido; CSV com o nome `knobridge-uso-<grupo>-<de>-<até>.csv`). `usageRecorder(report)` guarda a query string do relatório e do CSV. Variações: `usageAs(report)`, `usageFails(status, code)`, `usageCsvFails(status, code)`, `usageCsvWithoutName`, `usageCsvPending`.
- `page.ts`: `page(request, rows)` (uma página honrando `limit`/`offset`), `matchesQuery(request, ...texts)` (busca `q` sem diferenciar maiúsculas), usados pelos handlers de listas, e `listRecorder(path, rows, texts)` (GET que filtra pelo parâmetro `query` como a API e grava a query string de cada pedido em `queries`; `last()` devolve a última sem `limit`/`offset`, com as chaves em ordem). Cada recurso com lista pesquisável exporta o seu: `providersRecorder`, `productsRecorder`, `collectionsRecorder`, `sourcesRecorder`, `membersRecorder`, `runnersRecorder`.
- `record.ts`: `recordingPost(path, respond)` (guarda os corpos JSON recebidos, para afirmar o que a tela enviou) e `pendingPost(path)` (nunca responde, para ver o estado de envio).

**Não entra aqui**: fábricas de dados (`../factories.ts`), testes, dados reais.

**Convenções locais**:

- Caminhos casam qualquer origem (`*/v1/...`), para não depender da `baseUrl`.
- Um handler padrão por endpoint usado pelo app (entra em `<recurso>Handlers` e em `handlers`); variações exportadas com nome que diz o cenário, para `server.use(...)`.
- Corpos de sucesso vêm de `../factories.ts`; erros, de `apiErrorResponse` com o `code` real do backend.
- Recurso novo: arquivo novo aqui e uma linha em `index.ts`.

**Como testar**: exercitada indiretamente por `pnpm test -- --coverage`, de `frontend/`.
